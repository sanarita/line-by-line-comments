# 全行コメント（ラインバイライン・コメント）

昔の優秀なVBAエンジニアの流儀に倣い、**すべてのコード行に「その行で何をしているか」の日本語コメントを付ける**。
目的は、AIが書いたコードを人間が一行ずつ読んで理解・説明・保守・監査できる状態にすること。

想定する場面：非エンジニアが引き継ぐコード（VBA・GASなど）、AIが書いたコードを人がレビュー・承認するとき、学習。
エンジニア同士で長く保守する本番コードには、後述の「納品版」（【理由】だけを残した版）を使う。

## 2種類のコメントを書き分ける

| 種類 | 書く内容 | 書く場所 | 目印 |
|---|---|---|---|
| **What（何をしているか）** | その行の処理 | **行末** | なし |
| **Why（なぜそうするか）** | 判断の根拠・背景 | **その行の直上に独立した1行** | 行頭に `【理由】` |

```python
total = 0  # 合計を入れる変数を0で用意する
# 【理由】CSVに空欄の行が混ざるため、数字でない行は飛ばす
for row in csv.reader(f):  # CSVを1行ずつ取り出す
    if not row[1].isdigit():  # 金額の欄が数字でなければ
        continue  # その行は飛ばして次の行へ進む
```

読む人は「行末＝何をしているか」「`【理由】` 行＝なぜか」と位置と記号で見分けられる。
`【理由】` で検索すれば判断の根拠だけを一覧できる。

## 基本ルール

1. **コードがある行は全部Whatコメントを付ける。** `End If`、`Next i`、`}`、`return`、`</div>`、変数宣言も対象。
   - 例：`Next i  ' 次の行へ進み、ループの先頭に戻る`
2. **Whatの付ける場所**：原則は行末。行が長い（目安80文字超）か、言語上行末に書けないときは**その行の直上**に書く。直上コメントは直下の1行だけを説明する。
3. **Whatは処理の意味を書く。** 構文の言い換えは避ける。
   - ✕ `i = i + 1  # iに1を足す`
   - ○ `i = i + 1  # 処理済みの行数を1つ増やす`
4. **Whyは次の場面で必ず書く**（それ以外は書かなくてよい）。
   - 別のやり方もあるのに、このやり方を選んだとき（例：`Integer` ではなく `Long`）
   - 数値・設定値に根拠があるとき（`8000`、`100`、`timeout=30` など）
   - セキュリティ対策（SQLインジェクション、XSS、機密の扱い）
   - 不具合・仕様・環境の制約を回避しているとき
   - 業務ルールや社内規程に合わせた処理
   - 一見ムダに見えるが、消してはいけない行
   - 書き方：`【理由】〜のため` `【理由】〜を避けるため` のように理由を言い切る。
5. **WhyとWhatを同じ行に混ぜない。** 行末コメントに「〜のため」と根拠まで書かず、根拠は `【理由】` 行へ分ける。
6. **直上にWhyとWhatの両方が必要なとき**（行末に書けない言語など）は、上から `【理由】` → What → コード の順に積む。
7. **関数・Sub・クラスの先頭に見出しコメント**：目的／引数／戻り値／副作用（ファイル書き込み、シート変更、API呼び出しなど）。
8. **ファイル先頭に概要コメント**：何をするファイルか、実行方法、前提条件。**概要の後には空行を1行入れる**（納品版で概要を残す範囲の目印になる）。
9. **専門用語には短い補足**を付ける（例：「辞書（キーと値の組を持つ入れ物）」）。非エンジニアの上司や引き継ぎ先も読めることを想定する。
10. **コメントとコードを必ず一致させる。** コードを直したら、その行のWhat・Whyも同時に直す。嘘のコメントはコメントなしより悪い（AIエージェントは古いコメントも指示として読んでしまう）。
11. **コメントに機密を書かない。** パスワード、APIキー、社内サーバ名やIP、顧客名はコメントにも書かない。特にHTMLコメントはブラウザの「ページのソース」で誰でも読める。

## 言語別のコメント記号と注意点

| 言語 | 記号 | 注意 |
|---|---|---|
| Python | `#` | 下の「Python」節を参照。 |
| VBA | `'` | 行継続文字 ` _` の後ろには書けない（構文エラー）。継続する文はまとめて直上に説明を書く。`Rem` は使わず `'` に統一。`Integer` より `Long` を使うなど型の選択は【理由】の典型。 |
| GAS / JavaScript / TypeScript | `//` | 複数行のオブジェクトや配列は各要素の行末に書く。 |
| SQL | `--` | 長いSELECTは列ごと・句ごとに行末コメント。 |
| シェル / PowerShell | `#` | 行継続（`\`、`` ` ``）の後ろには書けない。直上に書く。 |
| HTML | `<!-- -->` | 下の「HTML」節を参照。 |
| CSS | `/* */` | `//` はCSSではコメントにならず、次のルールごと壊れる。必ず `/* */`。 |
| Dockerfile | `#`（行頭のみ） | 下の「Dockerfile」節を参照。**行末コメントは不可。** |

複数行にまたがる1つの文は、書ける行には各行に、書けない行はその文の直上にまとめて説明する。

### Python

- 1行目の shebang（`#!/usr/bin/env python3`）や文字コード宣言には行末コメントを付けず、次の行に説明を書く。
- **1行のdocstring**は行末に `# 関数の説明文（help()で表示される）` のようなコメントを付ける。
- **複数行のdocstring**は内側にコメントを入れられないので、`def` の次の行に `# 以下は関数の説明文` と書いてからdocstringを置く（コメントはdocstringの扱いを変えない）。
- **複数行のSQLやテキスト**は `"""..."""` を避け、1行ずつの文字列を並べる書き方にする。Pythonは並んだ文字列を自動でつなぐので、各行の行末に説明を書ける。

```python
conn.execute(
    "CREATE TABLE IF NOT EXISTS articles ("  # articles という表を、まだ無ければ作る
    "id INTEGER PRIMARY KEY AUTOINCREMENT, "  # 記事ID：登録順に自動で連番を振る
    "title TEXT NOT NULL"  # 題名：文字列で、空は不可
    ")"  # 列の定義の終わり
)  # テーブル作成命令の終わり
```

### HTML（中のCSS・JavaScriptを含む）

- タグの行は `<!-- 説明 -->` を行末に付ける。閉じタグ（`</div>` など）にも「何の終わりか」を書く。
- `<style>` の中は `/* */`、`<script>` の中は `//` を使う（領域ごとに記号を切り替える）。
- `<!DOCTYPE html>` は必ず1行目に置き、ファイル概要コメントはその後ろに書く。
- `<textarea>` と `<title>` の中身ではコメントがそのまま文字として表示される。その要素の直上に書く。
- HTMLコメントの中に `--` を書かない（仕様違反）。
- 属性が多く複数行に分けたタグは、タグの直上に「各属性の意味」をまとめて書く。
- 公開ページでは、納品前にコメントを除去するビルド（minify）をかける選択肢も伝える。

### Dockerfile

- **コメントは行頭の `#` だけが有効。** `WORKDIR /app # 作業場所` のような行末コメントは、命令によっては値の一部として扱われ、ビルドが壊れたり意図しない設定になる。必ず**命令の直上の行**に書く。
- `# syntax=docker/dockerfile:1` などのパーサーディレクティブは**ファイルの一番上**に置く。その前にコメントを書くと無視される。概要コメントはその後ろに書く。
- `RUN ... \` で複数行に続く命令は、続きの行ごとに直上へ行頭 `#` のコメント行を入れてよい（Dockerが実行前に取り除く）。
- `ENV`、`ARG` には何の設定かを書き、値の根拠は【理由】に書く。秘密情報を `ENV` やコメントに書かない（イメージに残る）。

```dockerfile
# 【理由】コードを変えるたびに再インストールが走らないよう、一覧だけ先にコピーする
# 依存ライブラリ一覧をコピーする
COPY requirements.txt .
```

### VBA

```vba
' A列の空でないセルの数を数えてメッセージで表示するマクロ
' 使い方: 対象のシートを開いた状態で CountFilled を実行する

Sub CountFilled()  ' 処理の開始
    Dim cnt As Long  ' 空でないセルの数を入れる変数を用意する
    ' 【理由】Integerは32,767までしか扱えず、それを超える行数でエラーになるためLongにする
    Dim lastRow As Long  ' データが入っている最終行の番号を入れる変数を用意する
    lastRow = Cells(Rows.Count, 1).End(xlUp).Row  ' A列の一番下から上に向かって最初にデータがある行を探す
    ' 結果をメッセージボックスで表示する（行継続 _ の後ろには書けないため直上に記載）
    MsgBox "最終行: " & _
        lastRow
End Sub  ' 処理の終わり
```

## 解説版と納品版

- **解説版（既定）**：WhatとWhyの両方を全行に付けた版。レビュー、引き継ぎ、監査、学習用。
- **納品版**：先頭の概要コメントと `【理由】` 行だけを残し、Whatコメントを消した版。エンジニアが長く保守する本番コード用。
- 納品版はチェッカーの `--release` で解説版から機械的に作る（手で作り直さない）。Pythonは元と構文木が一致すること（動作が変わっていないこと）も自動で確認される。
- ユーザーが「納品用」「本番用」「Whyだけ」と言ったら、解説版を作ってチェックした後に納品版も作り、両方を渡す。

## 手順

1. いつも通りにコードを設計・作成する（コメントのために設計を歪めない）。
2. 上のルールに従ってWhatを全行に、Whyを必要な行に付ける。
3. **チェッカーで漏れを確認する。** このスキルのフォルダにある `scripts/check_comments.py` を使う。

   ```
   python3 scripts/check_comments.py <ファイル>            # 漏れの検査
   python3 scripts/check_comments.py <ファイル> --release  # 納品版の作成（HTML・CSS以外）
   ```

   「未記載」と「エラー」が0件になるまで直す。スクリプトが見つからない環境では、全行を自分で読み直して漏れを確認し、その旨を返答に書く。
4. 返答の最後に「コード行 N行 / コメント付き N行 / 【理由】 N行」と結果を一行で添える。

チェッカーの判定：
- Python：`tokenize` で正確に判定（文字列の中の `#` はコメント扱いしない）
- VBA・JS・SQL・シェル・PowerShell：文字列の外にある記号で判定。行継続（` _`、`\`）の次の行は、文の直上の説明で足りるとみなす
- HTML・CSS：`<!-- -->`・`/* */`・`//` のどれかで可。`https://` などのURLはコメント扱いしない
- Dockerfile：直上のコメント行のみ有効。行末 `#` はエラーとして報告
- VBEから書き出したShift_JIS・CRLFのファイルも読め、納品版は元と同じ文字コード・改行で書き出す

shebang行、`<!DOCTYPE html>`、`# syntax=` など、コメントの位置がルール上制約される行が「未記載」と出た場合は、直後に説明があれば許容してよい。その旨を返答に一言添える。

## やらないこと

- ユーザーが「コメント不要」「最小限で」と明示したときはこのスキルを適用しない。
- 既存コードの修正でユーザーのコメントがある場合は消さず、足りない行だけ補う。
- コメントで行数が増えても、コード本体を省略・短縮して帳尻を合わせない。
- Whatの行末コメントに根拠を書き足して長くしない（根拠は【理由】行へ）。
